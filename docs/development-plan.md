# 众生之门主题游戏开发计划

> 项目暂定名：众生之门 · 灵境初行  
> 文档日期：2026-10-13  
> 目标平台：桌面浏览器优先，兼顾手机横屏与触屏操作  
> 美术方向：横版像素、青绿色森林、灵力发光效果  
> 项目定位：非官方主题玩法原型；先验证单人核心体验，再逐步扩展

## 1. 项目目标

制作一个可以直接通过网页试玩的横版动作冒险游戏，提炼《罗小黑战记》“众生之门”中多物种、灵力运用、探索与冒险的吸引力。

核心体验是：**不同身体决定移动方式，不同灵力决定与世界交互的方式。** 同一片森林可以因为角色、能力和策略不同而产生不同路线。

开发顺序为：核心原型 → 多物种可玩 Demo → 小型完整单人版 → 4 人合作扩展。每阶段都有独立可测试成果，上一阶段的试玩反馈决定下一阶段的投入。

## 2. 原作启发与改编原则

研究依据包括 B 站番剧页面、剧集文字抄本和社区设定整理；未逐集观看视频。同人小说中的扩展设定不作为原作事实。

| 原作启发 | 游戏中的改编方向 |
| --- | --- |
| 不同物种由玩家扮演 | 先做猫、人类、鸟三类身体，突出路线差异 |
| 灵力与能力运用 | 用有限、明确的交互规则实现御金、凝冰、植物能力 |
| 死亡后重建角色 | 后续短局模式清除本局成长，保留图鉴或外观；首版用检查点降低测试成本 |
| 玩家可以担任 Boss | 后续考虑非对称挑战模式 |
| 领地与势力规则 | 先做一个有局部增益的据点，形成挑战或绕行选择 |
| 长期复杂任务 | 拆成每局可以完成的小目标 |
| 所有生物都是真人 | 初期由 NPC 填充环境，联机成熟后再开放部分角色给真人 |

原作规则不会全部照搬。例如死亡后等待半小时，对早期网页试玩的帮助有限，因此采用立即重试。首版也不实现现金交易、永久在线大世界或完整社会系统。

## 3. 目标玩法与完整循环

长期目标循环：

1. 选择身体及初始灵力。
2. 进入森林，识别地形与敌人。
3. 探索路线、寻找灵印、获得局内能力变化。
4. 决定战斗、绕行或挑战据点。
5. 击败守门者，开启出口并结算。
6. 解锁图鉴或外观，再尝试其他组合。

地图采用有上下分层、岔路和环路的横版结构。树冠、河面和洞穴应提供不同路线，而非整张地图只有一条平直道路。

## 4. 阶段与工作量概览

以下为一位有编程基础的开发者全职投入、使用简化或现成素材并有 AI 辅助时的粗略估算，包含必要的体验调整；不是交付承诺。全部原创美术、从零学习游戏开发或扩大内容规模都会增加时间。

| 阶段 | 交付物 | 粗估工作量口径 |
| --- | --- | --- |
| 阶段 1：核心原型 | 猫形态、两种灵力、森林测试关卡、敌人与完整通关流程 | 约 1—2 周，包含试玩迭代 |
| 阶段 2：可玩 Demo | 三种身体、三类灵力、分区地图与任务 | 从立项累计约 6—10 周 |
| 阶段 3：完整单人版 | 更多关卡、成长、存档、完整视听与平衡 | 从立项累计约 3—6 个月 |
| 阶段 4：4 人合作 | 房间、权威服务器、同步、断线恢复与多人测试 | 在稳定单人基础上额外约 2—4 个月 |

AI 可以加快代码与初始素材产出，但动作手感、关卡阅读、组合平衡与真人联机体验仍需要反复试玩。

## 5. 阶段 1：核心原型

### 5.1 范围

- 一个可操控的猫形态。
- 左右移动、二段跳、冲刺、灵爪近战。
- 御金：发射金属飞刃，远程攻击敌人。
- 凝冰：冻结敌人，在指定河流附近生成临时冰桥。
- 一片横向森林：出生之林、镜水溪、古树庭、灵境之门。
- 三枚灵印、普通敌人、一只守门者 Boss。
- 中途检查点、死亡复苏、重开与通关结算。
- 键盘与触屏按钮、暂停、操作指南、音效开关。

### 5.2 任务

- [x] 独立实现游戏状态与固定小步长模拟。
- [x] 实现移动、跳跃、落地、冲刺与攻击。
- [x] 实现灵力消耗、恢复及技能冷却。
- [x] 实现冰弹冻结与 9 秒冰桥。
- [x] 实现三枚灵印与通关条件。
- [x] 实现敌人、Boss 灵弹及生命判定。
- [x] 实现检查点、死亡复苏、暂停和重开。
- [x] 实现像素森林、视差、猫动画和技能反馈。
- [x] 实现页面界面、操作指南、触屏按钮及本地通关纪录。
- [x] 通过完整关卡路线的自动模拟测试。
- [ ] 完成用户真实浏览器试玩与反馈修正。

这里的完成状态对应本次已编写的第一阶段实现。发布结果以交付时提供的 Sites 链接为准；自动测试通过不等于已完成真人手感验收。

### 5.3 当前操作

| 操作 | 键位 |
| --- | --- |
| 左右移动 | A / D 或左右方向键 |
| 跳跃、二段跳 | Space；也支持 W / 上方向键 |
| 灵爪近战 | J |
| 御金 | K |
| 凝冰 | L |
| 冲刺 | Shift |
| 暂停 / 继续 | Esc / P |
| 开始、复苏、继续 | Enter，或页面按钮 |

### 5.4 当前实现与原计划的调整

为交付一个独立、可直接部署的首版，当前实现使用 **原生 Canvas + JavaScript ES Modules**，画面由代码绘制，不依赖外部 CDN。先前建议的 TypeScript + Phaser 保留为扩展阶段的评估选项，并非当前代码已经使用的技术栈。

当前原型包含一只猫、御金与凝冰两类能力；尚未实现三物种、植物能力、正式领地系统或多人游戏。死亡复苏保留本次灵印，属于早期测试模式。

### 5.5 验收标准

1. 从初始出生状态可以正常完成收集、战斗和通关，无位置修改或奖励作弊。
2. 河流至少能通过冰桥或上方跳跃路线解决。
3. 冰桥到期会消失，冻结敌人会恢复行动，技能有清晰反馈。
4. 二段跳、冲刺、受击与暂停不会导致卡死。
5. 死亡后可以复苏，已收集灵印正确保留；整局重开正确清空。
6. 灵印不足或 Boss 未击败时不能通关。
7. 实际试玩者能理解目标、找到操作方式，并愿意重试。

### 5.6 第一轮试玩重点

- 猫是否太小、与背景对比是否足够。
- 跳跃高度与横向速度是否容易掌握。
- 第二枚灵印需要二段跳，是否有足够提示。
- 冰桥续时、敌人冻结、灵力不足是否清楚。
- 近战与远程攻击是否都有使用价值。
- Boss 难度、失败后的重试成本是否合适。
- 桌面与手机横屏是否出现按钮遮挡或滚动干扰。

## 6. 阶段 2：多物种可玩 Demo

目标是把核心原型扩展为具有重玩价值的短局冒险，单局目标时长约 15—25 分钟。此时长是未来 Demo 的设计目标，不是当前小关卡的保证用时。

### 6.1 身体与能力

| 身体 | 独有移动方式 | 需要的关卡支持 |
| --- | --- | --- |
| 猫 | 攀墙、窄洞通行、灵活跳跃 | 攀爬面、狭窄通道、树冠落点 |
| 人类 | 使用工具与机关 | 开关、推拉物、可操作装置 |
| 鸟 | 短时飞行或滑翔 | 高差路线、落脚点、飞行资源约束 |

| 灵力 | 初始技能方向 | 与环境的关系 |
| --- | --- | --- |
| 御金 | 投射、牵引指定金属物件 | 攻击、搬运、触发机关 |
| 凝冰 | 冻结敌人、冻结指定水面 | 控制战斗节奏、创造路线 |
| 植物 | 藤蔓落脚点、缠绕 | 临时平台、限制敌人行动 |

这些是游戏改编设计，不代表原作有完全一致的技能限制。

### 6.2 任务

- [ ] 角色选择与三种身体。
- [ ] 三类灵力，每类两个基础技能。
- [ ] 身体与能力配置分离，支持九种基础搭配。
- [ ] 6—8 个相连房间，设置替代路线与回环。
- [ ] 至少一个可以挑战或绕行的据点。
- [ ] 完整任务链、一个 Boss 和退出结算。
- [ ] 短局死亡规则：局内成长清除，图鉴与外观可保留。
- [ ] 为技能交互建立组合测试表。

### 6.3 验收标准

- 三种身体在路线或解决方式上有明显差异。
- 各基础搭配均能完成主任务，专属捷径不构成通关软锁。
- 鸟的飞行不能直接跳过全部挑战。
- 冰、藤蔓、金属物件组合不会把玩家永久困住。
- 至少有两种不同策略能解决一个关键障碍。
- 单局节奏和失败成本经过实际试玩调整。

## 7. 阶段 3：小型完整单人版

目标是形成内容完整、能稳定保存进度并持续重玩的版本。

### 7.1 内容与系统

- 扩展少量风格明确的区域，例如森林、山壁、遗迹。
- 增加敌人行为与 Boss 阶段，不单纯增加生命数值。
- 扩充局内技能变化、图鉴、外观和解锁目标。
- 支持存档版本迁移、设置持久化和存档导入导出。
- 统一像素尺寸、调色板、动画节奏、UI 与音效。
- 补全新手引导、任务提示、失败原因和通关反馈。
- 根据实际目标设备做性能与兼容性测试。

### 7.2 验收标准

- 主要内容可完整通关，保存与恢复可靠。
- 不同能力组合具有选择价值，避免单一能力覆盖所有场景。
- 长时间游玩后无明显内存持续增长或状态堆积。
- 在明确记录的目标设备上检查帧率、输入响应与加载体验。
- 跨浏览器检查键盘、音频解锁、全屏、触屏和页面切换。

## 8. 阶段 4：4 人合作扩展

前提：单人移动、碰撞、伤害与技能规则已经稳定。

### 8.1 网络方案

采用房间制合作副本。客户端提交输入，服务器确认位置、伤害、道具、死亡和任务结果。客户端负责画面、输入反馈和必要的预测。

技术候选：Node.js + Colyseus。其房间、匹配和状态同步可以作为基础；具体战斗同步、延迟处理和负载需要另行验证。

当前 Sites 静态版本只承载浏览器客户端。普通 Node.js/Colyseus 长连接服务不能假定直接沿用静态托管方式，需单独选择支持该运行方式的服务端部署环境，或重新评估兼容的实时后端。

### 8.2 任务

- [ ] 创建、加入与退出房间，最多 4 人。
- [ ] 权威服务器执行核心规则。
- [ ] 服务端确认道具领取、Boss 状态与结算。
- [ ] 位置插值、必要的客户端预测和纠正。
- [ ] 掉线重连、玩家退出、房间销毁。
- [ ] 合作难度与重复技能交互。
- [ ] 弱网测试与负载测试。

建议先验证 50 / 100 / 200 ms 等不同延迟条件，再决定网络体验是否达到上线要求。不要在缺少实测时承诺同房人数或服务器容量。

### 8.3 后续可选玩法

- 一人控制 Boss，其他玩家挑战。
- 多物种协作，例如鸟探索、猫穿洞、人类操作机关。
- 小规模限时据点争夺。

大规模开放世界、永久领地、公会经济和所有生物均由真人控制，另行评估，不纳入本轮四阶段的承诺范围。

## 9. 技术与架构

### 9.1 当前原型

| 层 | 实现 | 职责 |
| --- | --- | --- |
| 模拟 | engine.js | 移动、碰撞、攻击、技能、敌人、任务、状态 |
| 渲染 | render.js | 像素角色、视差森林、场景、特效 |
| 交互 | main.js | 键盘/触屏输入、HUD、弹层、音效、本地纪录 |
| 页面 | index.html + style.css | 响应式布局、控制面板、帮助 |
| 验证 | test-engine.mjs | 单项回归与完整路线模拟 |
| 发布 | ChatGPT Sites | 静态站点托管与版本发布 |

### 9.2 扩展原则

- 模拟不依赖 DOM，便于自动测试及未来服务端复用。
- 身体、技能、敌人、任务和地图逐步配置化。
- 静态地图与局内动态状态分开。
- 明确技能的可作用对象，避免一开始引入任意物体真实物理模拟。
- 单人阶段使用本地保存；多人阶段由服务端确认持久化数据。
- 当关卡编辑、碰撞和素材管理成为实际瓶颈时，再评估迁移 Phaser + TypeScript 的收益与成本。

## 10. 主要难点与控制方法

| 难点 | 影响 | 控制方法 |
| --- | --- | --- |
| 战斗手感 | 能运行但不好玩 | 小关卡反复试玩，调整前摇、受击、镜头与速度 |
| 能力组合膨胀 | 新技能破坏旧地图 | 限定对象与规则，维护组合验收表 |
| 飞行/传送绕过挑战 | 地图失去意义 | 设置资源约束、路线条件和必要落脚点 |
| 像素动画产量 | 美术工作超出预期 | 统一规范，先完成少量身体，再扩展 |
| 多人延迟与状态分歧 | 命中与位置不一致 | 权威服务器、预测纠正、弱网实测 |
| 真人生物不足 | 世界空旷、玩法无法运行 | NPC 保持基础生态，逐步开放真人角色 |
| 范围失控 | 长期没有可交付版本 | 每阶段通过验收后才增加系统 |

## 11. 测试与交付记录

当前已执行：

- JavaScript 语法检查。
- 页面引用与入口资源存在性检查。
- 落地、二段跳、技能冷却与冰桥生命周期测试。
- 近战、远程、冻结与解冻测试。
- 检查点、死亡复苏、灵印保留、重开测试。
- 通关条件及致命伤害优先于通关的边界测试。
- 从默认出生状态使用普通输入完成全关卡的模拟测试。
- Canvas 游戏帧绘制与图像检查。

验证限制：本次执行环境缺少受支持的浏览器测试入口，因此尚未完成真实浏览器页面、键盘/触屏输入、音频及全屏的端到端测试。发布后首先收集这部分反馈。

## 12. 下一轮工作优先级

1. 用户在 Sites 上测试第一阶段，记录无法操作、目标不清楚、跳跃困难和战斗无反馈的问题。
2. 修复阻断性问题，调整角色可见性、手感与提示。
3. 验证河流的两条路线，以及御金/凝冰各自的使用价值。
4. 稳定核心玩法后，增加第二种身体和一种新交互，验证扩展结构。
5. 达到阶段 2 的验收条件后，再安排更多内容与联机。
